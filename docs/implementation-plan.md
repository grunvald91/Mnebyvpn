# Roadmap и приёмка MNEBYVPN

Все этапы ниже — **план**. GitHub Actions и серверы не запускались в рамках подготовки архитектуры.

## Этап A — архитектура (текущий)

- [x] Описана универсальная схема clients → subscription → Xray/Remnawave.
- [x] Разделены коммерческий backend, control plane, data plane и subscription delivery.
- [x] Учтены существующие VPS и подтверждённые ограничения RAM/диска.
- [x] Добавлены сценарии изолированной миграции, rollback, безопасности и спецузлов.
- [ ] Владелец согласовал выбор MVP и изменение ресурсов ru-edge.

**Выход:** набор документов, без серверных изменений.

## Этап B — безопасный preflight до установки

- [ ] Обновить инвентаризацию обоих VPS (полная карта nginx/SNI/ports/firewall/служб).
- [ ] Проверить подозрительную SSH-активность/журналы безопасности и меры доступа.
- [ ] Получить зашифрованные внешние бэкапы, проверить восстановление.
- [ ] Решить вопрос ресурсов: resize одного VPS или иной согласованный вариант.
- [ ] Проверить доступный домен и DNS для стабильного HTTPS subscription URL.
- [ ] Согласовать план совместной работы существующего Xray и Remnawave Node.

**Gate:** подписанное решение на изменяющие команды; без него только read-only.

## Этап C — тестовый control/data plane

- [ ] Изолированная установка Remnawave Panel/DB/Subscription Page на VPS после preflight.
- [ ] Подключение тестового Remnawave Node, без изменения действующего :443.
- [ ] Тестовая подписка VLESS/REALITY, версия Xray зафиксирована.
- [ ] Подписочный формат определяется корректно на минимум 2 клиентах.
- [ ] Испытаны revoke/expiry и восстановление при потере панели.
- [ ] Получены эксплуатационные CPU/RAM/диск/latency, резервная копия восстановлена.

## Этап D — коммерческий MVP

- [ ] TypeScript API с каталогом тарифов/entitlements.
- [ ] PostgreSQL, migrations, outbox worker, Remnawave adapter.
- [ ] grammY Telegram-бот: купить, получить подписку, продлить, инструкция, помощь.
- [ ] Провайдер оплаты с официальной поддержкой выбранного статуса самозанятого и СБП — выбрать по проверенным условиям.
- [ ] Подпись webhook, idempotency, платёжная сверка, retry/compensation.
- [ ] Тесты: два одинаковых webhook = одно продление; платёж без provision = восстановимая задача; revoke после expiry.
- [ ] Простейший защищённый кабинет и выбор доступного клиента по платформе.

## Этап E — испытания, релиз и рост

- [ ] Тесты в нескольких российских операторских сетях, не только с VPS.
- [ ] Не менее двух проверенных iOS клиентов, двух Android и одного Windows (доступность App Store — факт теста).
- [ ] Измерение разных транспортов по критериям совместимости, доступности и нагрузки.
- [ ] Планы мониторинга узлов, алертов, хранения данных и бэкапов.
- [ ] Постепенная выдача пользователям, не переключая старые Telegram-прокси.
- [ ] Зафиксированы лимиты ёмкости/стоимости и критерии добавления новых узлов.
- [ ] Исследовать `special` узлы только с договорной и сетевой проверкой.

## Минимальный критерий готовности к платной эксплуатации

- Есть домен подписки с HTTPS; он обновляется в подтверждённых приложениях.
- При окончании срока **существующий** ключ перестаёт подключаться.
- Платёжный webhook проверен и идемпотентен, восстановление после сбоя учтено.
- Есть проверенная инструкция backup/restore и offsite backup.
- Действующие Telegram-прокси продолжают работать; нет конфликта 443.
- Есть мониторинг ресурсов и понятный регламент действий при отказах.
- Не делаем заявлений о гарантиях работы на всех сетях/во время белых списков.

## Минимизация расходов

До preflight: 0 новых VPS, 0 production-развёртываний, 0 CI-minutes на документацию. Для следующего этапа предпочитать read-only SSH или проверенные инструменты; GitHub Actions использовать для одного объединённого диагностического запуска/необходимого деплоя, а не частых проб.
