# MNEBYVPN — Telegram-напоминания об окончании VPN

## Требование

Для **подтверждённой оплаченной VPN-подписки** отправляются два напоминания
через действующего `@MnebyVPN_bot`:

- за ~3 дня до окончания: при остатке более 48 и не более 72 часов;
- за ~1 день до окончания: при остатке более 0 и не более 24 часов.

Сообщение содержит реальную дату окончания доступа по московскому времени
и кнопку `🔁 Продлить VPN`, которая выполняет существующий callback
`nav:renew` в Telegram-боте. Резервный путь — сайт
`https://mnebyvpn.site/#plans`. Автопродление/списание не включаются.

**Пробные 24 часа не получают однодневное напоминание сразу после активации.**
Напоминаем о оплаченной подписке только если у entitlement есть
неотозванная запись `entitlement_credits`, связанная с `orders.state='PAID'`.
Также обязательно `entitlements.state='ACTIVE'`, известное `expires_at`,
подтверждённая последняя ревизия VPN-узлом в `provisioning_state`, а также
верифицированный `accounts.telegram_user_id`. Пользователи только с email
без привязанного Telegram не получают Telegram-уведомления.

## Идемпотентность, продления и отказы

Миграция `db/migrations/0021_vpn_expiry_reminders.sql` создаёт durable outbox
с первичным ключом `(entitlement_id, days_before, expires_at)`.
После успешной отправки записывается `SENT` и `sent_at`: обычные
повторные проходы worker не дублируют сообщения. При продлении или возврате
переход к новой ревизии/сроку заставляет старую запись стать `SKIPPED` либо
невыполнимой; при достижении нового окна будет сформировано **новое**
сообщение для нового срока. Привязка аккаунта к Telegram нужна до окна.

Задачи обрабатываются с PostgreSQL `FOR UPDATE SKIP LOCKED`, лимит
12 сообщений за 60 секунд на один worker. Выдача claim имеет lease
120 секунд, тайм-аут Telegram API 7 секунд. Ошибки 429 учитывают
`parameters.retry_after`, прочие сетевые сбои — ограниченный
экспоненциальный backoff (не более 8 попыток). Telegram 400/403 переводят
задачу в `FAILED`, чтобы не пытаться бесконечно доставлять человеку,
не открывшему бота или заблокировавшему его. Сообщения не содержат VPN-ключей.

Telegram Bot API `sendMessage` не предоставляет стандартного
идемпотентного ключа. Если Telegram принял сообщение, но произошёл timeout,
после восстановления worker возможен редкий дубль. Это **at least once**
при неудачах, а не гарантия идеальной однократной доставки. Когда Telegram
недоступен всё время выбранного окна, уведомление может быть пропущено.

## Выпуск

1. Применить миграцию 0021 на **той же канонической бизнес-БД**, которую
   использует действующий VPN-worker. Backup, проверка SQL и CI обязательны.
2. В приватном `runtime-vpn.env` системного пользователя worker
   явно установить:
   `VPN_EXPIRY_REMINDERS_ENABLED=yes` и
   `TELEGRAM_BOT_TOKEN` **существующего** @MnebyVPN_bot.
   Значения secrets не публиковать, не логировать и не добавлять в Git.
   BotFather/Telegram webhook secret не заменяет Bot API token
   для инициативной `sendMessage`.
3. Перезапустить только `mnebyvpn-vpn-worker.service` после установки
   миграции и env. Отдельный systemd unit не создаётся; цикл напоминаний
   асинхронен и не блокирует provisioning loop.
4. Проверить точные переходы, дедупликацию, заблокированный чат,
   `retry_after`, досрочное продление и хотя бы один **контролируемый
   тестовый Telegram-чат**. Проверка PostgreSQL offline не доказывает,
   что бот может отправлять сообщения в production.
5. Источник статусов: `vpn_expiry_reminders` и обезличенная строка
   `vpn-expiry-notifications` в журнале worker.

Токен должен принадлежать тому же боту, который пользователи уже
запускали в Telegram. Бот не может самостоятельно начать личный диалог
с пользователем, который с ним ещё не взаимодействовал.
