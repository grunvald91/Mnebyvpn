# P1 — истечение VPN-доступа при потере control plane

Дата: 2026-11-05. **СТАТУС: BLOCKED UNTIL VERSIONED TEST.**

## Несовместимые без дополнительной проверки требования

- Платная подписка обязана истекать **на data plane**, даже если уже импортированный клиент сохранил старую конфигурацию.
- При недоступности Remnawave Panel работающий Node может продолжить обслуживание по локальной конфигурации.
- Из этого **нельзя вывести**, что Node самостоятельно проверяет `expires_at` без связи с панелью или закрывает существующие соединения в срок.

Нельзя утверждать, что конкретная версия Xray/Remnawave умеет автономно отзывать доступ, пока этого не подтвердят тесты **пинованных версий**. Проблема также относится к `refund/revoke`: это событие может не дойти до узла в период partition.

## Политика и варианты реализации

- Ввести параметр продукта `max_stale_entitlement_seconds` **только после измерений и согласования**. Пока значения нет, платный запуск BLOCKED.
- A) Если узел сам обеспечивает локальную дату окончания на уровне соединений/пользователей: задокументировать verified version, механизм хранения, timezone/clock drift, restart и expiry existing connections.
- B) Иначе: спроектировать отдельный ограниченный локальный enforcement agent/lease (только подписанное актуальное состояние и доверенный local clock, без раскрытия Remnawave API). Это **отдельная новая подсистема**, требует собственной проверки безопасности; не считать бесплатным решением.
- C) Если доступен только контроль панели и его недоступность не ограничена — не продавать доступ с обещанием строго гарантированного автоистечения; вначале реализовать управляемое окно stale access с мониторингом и аварийным playbook либо заменить архитектуру.
- Любой вариант должен явно описывать новые подключения **и уже установленные TCP/UDP сессии**, максимум запаздывания отзывов, и бизнес-обещание пользователю.

## Partition acceptance

1. Создать тестового пользователя с коротким `expires_at`, импортировать профиль и подключиться.
2. **До** срока истечения отключить канал Panel↔Node (в тестовой среде); убедиться, что data plane продолжает работать только в документированных рамках.
3. Дождаться `expires_at`; проверить **новое подключение** и **уже существующую сессию** на TLS, TCP и при необходимости UDP.
4. Замерить реальное stale окно; повторить с Node restart, reboot, clock skew/time sync, восстановлением связи и повторной синхронизацией.
5. Повторить отдельно сценарий ручного `SUSPENDED` / refund при потере связи.
6. **PASS только при соответствующем зафиксированной политике поведении**; в противном случае статус продукта остаётся NOT READY.

Параметры stale window, механизм автономного enforcement, реальная надёжность Node на network partition не подтверждены. Источник архитектуры компонентов: https://github.com/remnawave/backend ; https://github.com/remnawave/node .
