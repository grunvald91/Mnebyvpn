# MNEBYDNS #84 — этап 4: изолированный localhost TCP relay с метрикой байтов

## Что реализовано

Новый `packages/dns-ingress/src/metered-relay.ts` — **встраиваемый модуль**, не создающий публичных TCP-портов. Он получает **уже установленные** сокеты клиента и upstream, а также идентичность подписки, **проверенную отдельно на transport-уровне**. Никаких публичных DNS, SNI-map и nginx изменений этим PR нет.

В обоих направлениях:
1. Перед передачей каждой порции (настраиваемый верхний предел 1–65 536 байт) вызывается SQL `reserve_smart_dns_chunk`.
2. До записи проверяются действительность подписки/ревизии, лимит размера, срок окончания короткой аренды `allowed_until`, отсутствие ошибки СУБД.
3. В TCP `Socket.write` отправляется **не больше размера резерва**; по callback вызывается `settle_smart_dns_chunk` с указанием направления. При невозможности списания TCP прекращается, HOLD остаётся для расследования.
4. Параллельно клиентское соединение периодически проверяет `ACTIVE`/оплаченность, `expires_at`, `quota_state` и актуальность provisioning ACK. При отказе разрываются **оба** сокета. Параметр для лабораторного теста `recheckMs` 20–1000 мс (по умолчанию 200).
5. Если транспорт не передал надёжно проверенный `entitlementId + revision`, модуль отказывает и закрывает сокеты. Ни исходный IP клиента, ни DNS hostname, ни SNI стороннего сайта не принимаются в качестве аутентификации абонента.

`packages/dns-ingress/src/postgres-chunk-quota.ts` — адаптер SQL 0111/0110 с получением `allowed_until`; ни один положительный ответ `RESERVED` не интерпретируется как доказательство сетевого доступа.

## Реальные локальные интеграционные испытания

`tests/integration/dns-loopback-metered-relay.test.ts` создаёт два TCP listener на **127.0.0.1 с динамическими портами**, а не на внешнем интерфейсе: локальный echo upstream и локальный ingress. Для теста идентичность подписки назначает **сам тестовый сервер** конкретному listener; это искусственная доверенная привязка, которая НЕ доказывает работу персонального Android DoT в интернете. С PostgreSQL проверяются:
- TCP payload `client→upstream` и `upstream→client`, фактическое добавление upload/download в SQL журнал и расход общей квоты;
- смена подписки на `EXPIRED` во время открытого TCP соединения — наблюдение фактического закрытия сокета;
- отсутствие доверенной идентичности — закрытие соединения без отправки данных.

## Критические границы / НЕ заявлять готовность продажи

- **Client attribution unverified**: доставка персонального DNS-запроса не связывает отдельный TCP поток с подпиской, а на текущих VPS нет публичных IPv6 ([фактическая диагностика](https://github.com/grunvald91/telegram-proxy-infra/actions/runs/42793733014)). Персональный destination-IPv6 в продакшне невозможен без реального префикса и client E2E; Android IPv4-only надо проверять отдельно. Ни один из модулей не принимает подключение из интернета и не заменяет эту проблему.
- **Socket.write ≠ proof of wire delivery**: callback означает, что байты обработаны Node writable, но **не доказывает**, что peer получил каждый байт, и не охватывает IP/TCP/TLS накладные расходы. Для денежного учета нужны PCAP/сетевые измерения, точное определение billing units и оценка overshoot.
- **Expiry during write or DB failure**: ответ `settle` после expiry/refund пока может не пройти; SQL сохраняет HOLD, а журнал принятой квоты может не включить байты, уже переданные в TCP. Нужны отдельный аудитируемый поздний settlement и безопасная передача контекста на другой узел.
- **Latency and mid-chunk revocation**: время проверки допуска и передачи не атомарно, изменения могут произойти после последнего `active` и до `write`. Прототип ограничивает окно размером chunk, timeout записи и периодическим опросом, но не обеспечивает математический нулевой overshoot. Не проведены испытания при реальных задержках и внезапных сетевых разделениях.
- **Синтетическая идентичность**: localhost тест **не** проверяет защищённое CONNECT/SOCKS, токены, секреты, NAT, Nginx, ECH/QUIC, TLS termination, SNI или реальный DoH/DoT. Для альтернативного explicit proxy отдельный authenticated CONNECT listener и TLS обязательны; в данном PR они отсутствуют.
- **Клиентский URL и коммерческий checkout** остаются выключенными. Никаких действий на продакшен-серверах.

## Следующий критерий GO/NO-GO

Для *DNS-only* получить у хостера реальный маршрутизируемый IPv6 адрес/префикс либо найти другой технически проверенный per-stream identity, совместимый с системным Private DNS Android **и IPv4-only**. На двух узлах в текущей конфигурации IPv6 нет, и обещать персональную DNS-only ссылку с достоверным подсчётом HTTPS гигабайтов нельзя.

Для *варианта с приложением/профилем прокси* сначала разработать отдельный явный authenticated CONNECT/SOCKS транспорт, провести сетевое E2E при CGNAT, нескольких устройствах и двух серверах. Это **другой способ подключения**, его нельзя называть прежней DNS-only услугой.
