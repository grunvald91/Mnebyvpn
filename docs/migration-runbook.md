# Runbook: безопасная миграция без очистки действующих VPS

**Статус: не выполнялось.** Этот документ — последовательность допусков и шагов. Ничего из перечисленного не разрешает автоматически изменение серверов.

## Правило STOP

Не выполнять `rm -rf`, переустановку ОС, очистку Docker, отключение nginx/telemt/mtg/redsocks/WireGuard, изменение :443, `ufw reset`, замену Xray или смену DNS до (а) проверенного внешнего бэкапа и (б) отдельного подтверждения владельца.

## Фаза 0 — read-only инвентаризация

- Источник текущей конфигурации: `grunvald91/telegram-proxy-infra` и **живая система**, а не только старые сохранённые файлы.
- Сверить все IP/ports/SNI/services/route maps **без публикации секретов**.
- Проверить доступ к SSH по резервному каналу и последнюю версию systemd, Docker, nginx, WireGuard, Xray.
- Проверить безопасность (пользователи, ключи, доступные admin endpoints, аномальные процессы).
- Проверить ресурсы и запас по памяти/диску после возможного увеличения ru-edge.

**Gate 0:** инвентарь и план портов подтверждены. Сейчас частично имеется аудит, но свежая полная карта сервиса/портов НЕ подтверждена.

## Фаза 1 — бэкапы и восстановление

- Создать актуальный backup разрешённых конфигураций и БД **с защитой секретов**; хранить за пределами VPS.
- Отдельно сохранить рабочие бинарники/версии, nginx stream, WireGuard, systemd и DNS-records.
- Пробно восстановить всё в изолированной среде или провести подтверждённую выборочную проверку восстановления.
- Восстановительные секреты не класть в GitHub, issue, workflow artifacts публичного репозитория.

**Gate 1:** проверенные backup, процедура возврата и контрольные суммы готовы.

## Фаза 2 — окружение / ресурсы

- Согласовать resize ru-edge; выполнить backup/restore проверку до операции хостера.
- Выделить namespace/paths/контейнерные сети без конфликта с прокси; разобрать SNI и firewall.
- Закрепить версии/дигесты upstream-образов, подготовить минимальные конфиги.
- Административный доступ к панели только через защищённый путь; не открывать админ API на публичный IP без необходимости.

**Gate 2:** ресурсы/порты проверены, rollback доступен, изменение допущено владельцем.

## Фаза 3 — изолированная тестовая установка

- Сначала Remnawave Panel в отдельном проекте на ru-edge после resize, без изменения существующего ingress.
- Затем тестовый Remnawave Node на foreign-exit **параллельно действующему host-Xray**, с отдельным тестовым портом и без переписывания 443/nginx.
- Проверить heartbeat Node, версию Xray, тестовый пользователь, импорт клиентом и исходящее соединение.
- Если один порт/адрес мешает сосуществованию, не переделывать SNI «на лету»; остановить этап и подготовить согласованную миграцию трафика.

**Gate 3:** минимум два рабочих клиента, проверка отключения доступа, тест восстановления и отсутствие регрессий текущих прокси.

## Фаза 4 — коммерческий слой

- Backend с идемпотентными платежами и адаптером Remnawave; бот, инструкция подключения.
- Staging-тесты без реальных платежей. Затем согласованная проверка провайдера и production-платежей.
- Документировать SLA/ограничения, а не обещать абсолютный доступ.

**Gate 4:** smoke/e2e матрица, безопасность, мониторинг, резервный канал управления, backup/restore — PASS.

## Фаза 5 — перевод нагрузки

- Canary-трафик малой группы с метриками, затем постепенное увеличение.
- Старые Telegram-прокси не удалять автоматически. Отдельное решение о выводе из эксплуатации с датой, замером нагрузки и подтверждением владельца.

## Проверка после каждого вмешательства

- Существующие Telegram-прокси работают из клиента.
- Нет конфликта 443/SNI/HTTPS приложений.
- Работают SSH и WireGuard, нет существенного роста потерь/latency.
- На узлах есть свободная память и диск, нет новых ошибок OOM/log spam.
- Бэкапы и мониторинг работоспособны.

## Rollback

При любом REGRESSION → прекращаем расширение, отменяем новые маршруты/профили, возвращаем предыдущие закреплённые образы/настройки, сверяем hash и действующие сервисы. **Не удаляем** подтверждённые рабочие старые конфигурации до полного восстановления.

## Ответственные решения

- Подключение VPS / установка ПО / изменение firewall / resize / деплой / удаление — только после отдельного явного решения владельца.
- Изменения документации и тестов без контакта с production могут выполняться независимо.
