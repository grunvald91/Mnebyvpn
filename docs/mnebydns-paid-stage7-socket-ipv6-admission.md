# MNEBYDNS #84 — этап 7: идентификация платного соединения по destination IPv6

## Реально реализовано

1. `db/migrations/0114_dns_socket_ipv6_admission.sql` добавляет `dns_ingress_identify_destination_ipv6(inet)`. Функция получает платную идентичность через уже проверенный SQL-0109 (уникальный адрес, действующий оплаченный кредит, подтверждённая revision, неистёкший срок). EXECUTE выдаётся **только** отдельной роли `mnebyvpn_dns_ingress`; обычный пользователь сайта и оператор сверки такого доступа не получают.
2. `packages/dns-ingress/src/socket-ipv6-identity.ts` получает реальный `socket.localAddress` из **уже принятого TCP сокета**. Это не данные DNS-запроса и не пользовательский `Host`/`SNI`/`X-Forwarded-For`. Неизвестный адрес, IPv4, IPv4-mapped IPv6, уже уничтоженный сокет, ошибка или timeout базы — отказ без перехода на другую подписку.
3. Unit tests — негативные IPv4/mapped, неподтверждённый IPv6, ошибка/зависание БД.
4. PostgreSQL negative SQL contract — неоплаченный/неактивированный endpoint, отсутствие применённой revision, правильная индивидуальная связь, отказ чужому destination IPv6, IPv4 и отзыв подписки, разграничение ролей.
5. Локальный integration test — **настоящий IPv6 loopback `::1`**, на котором TCP-сервер принимает соединение; до подключения к upstream сервер сверяет `socket.localAddress` с БД и только после этого запускает TCP-реле с предоплаченными резервами. Тест отдельно подтверждает отказ по IPv4 TCP. Это **НЕ** подтверждение работы маршрутизируемого адреса за пределами машины.

## Почему это не готовый публичный продукт

**Нет выделенного маршрутизируемого IPv6 на нынешних двух серверах** ([read-only audit](https://github.com/grunvald91/telegram-proxy-infra/actions/runs/42793733014)). Локальный `::1` в CI искусственно зарегистрирован как индивидуальный адрес **исключительно для теста**. Пользовательский Android/iPhone не сможет подключиться к этому адресу через интернет.

`socket.localAddress` даёт проверяемый адрес назначения уже принятого TCP соединения, но **не доказывает**, что этот адрес выделен ровно одному покупателю у хостера. Поэтому нужен внешний инфраструктурный аудит: показать реально полученный публичный IPv6 / префикс, server-side маршрут до NIC, привязку Linux TCP listener к destination IP, запрет wildcard/IPv4 downgrade и сертификат/TLS passthrough. Затем тесты мобильного оператора/Wi-Fi, Android Private DNS, iPhone DNS-профиля, IPv4-only, QUIC/ECH/DNSSEC и индивидуальной выдачи DNS-ответов вне shared cache.

### Почему не подменяем это "персональным портом HTTPS RR"

[Стандарт RFC 9460 §9.2.4](https://www.rfc-editor.org/rfc/rfc9460.html#section-9.2.4) прямо отмечает непригодность общих HTTPS DNS-записей для индивидуальных клиентских параметров; допустимый `port=` не гарантирует, что любой браузер направит запрос на персональный TCP порт, а обход DNS/собственный резолвер приложения и fallback могут сделать это поведение иным. Такой вариант нельзя выдавать за уже проверенную систему учёта.

## Точные блокеры

- **Production network identity** остаётся NO-GO без маршрутизируемого индивидуального IPv6 или другого подтверждённого authenticated data transport.
- **Strict delivery billing**: `Socket.write` и postgres settlement не являются сетевым PCAP и не гарантируют, что приложению доставлены каждый байт и ни одним больше.
- **Crash recovery and late money policy**: стадии 5–6 сделали видимым неизменяемый аудит и очередь расследований; восстановление расходов без подтверждённого node fencing и денежная корректировка после возврата оплаты **не автоматизированы**.
- Платный checkout и `WEB_DNS_METERING_VERIFIED` остаются выключенными. Работающий DNS, VPN и Telegram proxy на VPS не тронуты.

**PR является draft и требует отдельного ревью безопасности и реального клиентского E2E перед возможным релизом.**
