# P1 Gate — контроль доступа к SNI ingress

Дата: 2026-11-05. **СТАТУС: DEFERRED в MVP / BLOCKS ANY PAID MNEBYDNS SNI**. Это исследовательский контракт, не готовый механизм и **не P0 релиза VPN**. Актуальный реестр: [release-gates](release-gates.md).

## Уязвимость базовой схемы

Персональный токен в DoH запросе аутентифицирует только **DNS-запрос**. После получения IP браузер самостоятельно устанавливает TCP/TLS к SNI proxy. При обычном TLS passthrough прокси видит IP источника, SNI и иные доступные поля ClientHello, но **не получает персональный DNS-токен**. Прямой вызов `<ingress-ip>:443` с допустимым исходным SNI может обойти DNS и продолжить работу после отмены подписки. `nginx ssl_preread` не аутентифицирует оплаченного пользователя.

**Запрет для платной эксплуатации:** никакой продукт `smart_dns` с коммерчески ограничиваемым SNI ingress не выпускаем, пока proxy-side association of each connection with a subscription quota, plus enforceable revoke/exhaustion не доказаны. Один лишь DNS token/TTL/SNI allowlist/IP ACL нельзя считать таким механизмом.

## Кандидатные варианты — без утверждения выбора

| Вариант | Идентичность на входе TCP | Цена для UX / ограничения | Решение |
|---|---|---|---|
| Обычный DNS rewrite + общий SNI passthrough | Нет | Anyone с ingress IP и разрешённым SNI потенциально использует relay | Только изолированный функциональный PoC без платного допуска |
| DNS-токен + временная IP-авторизация | IP, **не подписчик** | CGNAT, смена IP, разные IPv4/IPv6, прямой доступ, злоупотребления | Не допускать как единственную защиту |
| Уникальный ingress IP на клиента | IP назначения | Дорогая адресация/масштабирование, связь IP ↔ клиент и отзыв, риск обхода за NAT | Исследовать экономику/реальность отдельно |
| Явный прокси (HTTPS CONNECT/SOCKS) с обязательной аутентификацией | Клиент передаёт credentials в отдельном протоколе | Нужно вручную настроить системный/приложенческий прокси; несовместимо с идеей «только сменил DNS» на всех устройствах | Приоритетный кандидат для **опционального authenticated proxy режима**, после OS теста |
| Собственный лёгкий агент/туннель | Данные сессионной аутентификации | Требуется приложение/профиль, по сути отдельный транспорт/VPN | Отдельный продукт/режим, не называть DNS-only |
| mTLS напрямую с исходным HTTPS origin | Клиентский сертификат принимает origin | TLS passthrough не аутентифицирует клиента как reverse-proxy; произвольные origins не обязаны поддерживать mTLS | Не считать универсальной реализацией |

Возможен отдельный **защищённый DNS-only продукт** с аутентифицированным resolver, но он не может обещать доступ через платный SNI relay и не равен VPN.

## Требуемая proxy-side contract спецификация до выбора реализации

- Откуда на ingress берётся независимое от DNS аутентифицированное право `account_id + entitlement_revision + expires_at`?
- Как прямой TCP клиент **без токена** получит отказ до передачи данных в origin?
- Как применяется revoke к **новому и существующему** соединению при отказе DNS/panel?
- Как обрабатываются разные внешние IPv4/IPv6 клиента, NAT, смена сети и несколько устройств?
- Какая библиотека/протокол обеспечивают именно аутентификацию, а не только whitelist SNI?
- Доказаны ли комфортное подключение на iOS/Android и приемлемая стоимость модели?

Если нет технически реализуемого варианта для прозрачного DNS-only UX, принять ADR: **перестать обещать оплачиваемый transparent SNI**, ограничиться DNS-only и отдельным явным authenticated proxy/VPN.

## Обязательные negative E2E тесты

1. Неоплаченный/отозванный/исчерпанный пакет, **невыданный** или пожизненно выведенный из эксплуатации destination IP → доступ к origin через proxy **DENY**. Если известен **активный оплаченный** bearer IP, владение этим адресом *не* доказывает личность: его использование расходует квоту владельца и технически допускается в модели без идентификации устройств.
2. Отмена/истечение подписки, сохранённый IP ingress и SNI → новое соединение **DENY**.
3. Отмена подписки, **открытое** соединение → поведение соответствует оговорённому TTL/разрыву; измерить, не считать автоматически закрытым.
4. Смена source IP, CGNAT, несколько устройств и добровольная передача профиля → трафик допускается только в пределах **одного активного пакета** и его общего лимита, без идентификации физических лиц. Неизвестный/перевыданный или выключенный destination IP → DENY; переиспользование адреса для другого пакета навсегда запрещено.
5. Ошибка/auth backend offline → новые платные соединения **fail closed**, если иной режим не утверждён и не испытан.
6. Персональный DoH token отозван, DNS cache у клиента сохранён → прямая попытка на ingress **DENY**.
7. Неизвестный SNI, invalid origin, private IP/SSRF → DENY.

Верхнеуровневая модель без секретов. Источники: https://nginx.org/en/docs/stream/ngx_stream_ssl_preread_module.html ; https://www.rfc-editor.org/rfc/rfc6066.html .

## Уточнение бизнеса: общая квота, не число устройств

Подписчик покупает единый пакет трафика и может использовать его на неограниченном числе устройств. Не требуется идентифицировать физического пользователя, HWID, source IP или отдельные устройства. Но каждый HTTPS поток **должен быть отнесён к subscription_id** и единому счётчику пакета. Кандидат — уникальный destination IPv6 для подписки (адрес выступает передаваемым bearer capability, его утечка позволяет третьим лицам расходовать чужую квоту). Существование доступного IPv6-префикса, маршрутизация, поддержка IPv4-only сетей и безопасное отключение пока НЕ проверены. Подробно: [ADR-0005](decisions/0005-shared-dns-quota.md). Блокер платного запуска — не отсутствие HWID, а отсутствие **проверенного учёта/ограничения на самом ingress**.

**Review 2026-11-05:** проблема не в «чужом человеке», а в оплаченном пакете, неизменном ingress attribution и жёсткой квоте. Доступ к активному bearer IP по договорённой модели можно передавать; сохранённый адрес после revoke/expiry не может дать доступ. Два одинаковых DNS имени для разных подписок должны вести на разные непереиспользуемые IP (см. [ADR-0005](decisions/0005-shared-dns-quota.md)).
