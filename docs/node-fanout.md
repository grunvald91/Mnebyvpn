# MNEBYVPN — этап 2: многосерверное предоставление доступа и подписки

Дата: 2026-11-07. **CODED / TESTED_OFFLINE после зелёного CI; NOT DEPLOYED.**
Базовая ветка содержит [этап 1](node-management.md) из PR #43.

## Новые функции

1. Миграция 0024 добавляет per-node fencing, наблюдения и очередь повторов.
   После изменения прав, срока, лимита или отзыва entitlement SQL-trigger обновляет
   желаемую ревизию **у всех** назначенных узлов, включая недоступные.
2. `packages/nodes/src/pg-fanout.ts` хранит независимое состояние узлов,
   использует session-level advisory lock на пару (entitlement,node), а также
   транзакционный CAS по revision и fencing при подтверждении.
3. `packages/nodes/src/fanout.ts` ограничивает параллельность; на каждый узел
   заново читает актуальные права, сверяет реальное node-side состояние и срок,
   безопасно обрабатывает unknown outcomes. Отказ узла не мешает отозвать доступ
   на остальных. Нет глобального ACK и нет изменения платежных статусов.
4. `packages/nodes/src/subscription.ts` проверяет существующий bearer-токен
   по SHA-256 и выдаёт только **подтверждённые, свежие** профили
   (действующий entitlement, независимый per-node ACK, verified node, health,
   строгая проверка VLESS/TLS/WS адреса). Повторно сверяет права перед возвратом.
   Текст с несколькими строками VLESS уже поддержан; HTTP route не подключён.
5. Для каждого узла свой независимый контроллер/ключ HMAC. Ключи не хранятся
   в реестре и должны приходить из приватного хранилища при реальном включении.

## Что НЕ включено

- Нет запуска этого многосерверного dispatcher в production worker, нет новой
  публичной /sub ветки, нет автоматических покупок VPS, смены сервера в клиентах
  или интеграции с panel. Старый подписочный URL работает по старому коду.
- Не принимаем SQL-маркеры approved/verified за E2E. Для каждого будущего узла
  нужны приватные реальные проверки, независимый hard expiry и доступность.
- Проверка соединения с новым физическим узлом, health probes в живой сети,
  автоматическая миграция пользователей и механизм смены протоколов ещё
  **BLOCKED**. Структура работает в изолированных тестах с синтетическими узлами.
- Перевод узла в disabled без изменения entitlement revision требует отдельной
  протокольной версии/сквозного теста: серверный агент может не принять команду
  opposite-state с той же ревизией. Профиль disabled узла больше не публикуется,
  а доступ на нём должен независимо истечь к hard-expiry. Критическая задача до
  операторского включения live-node draining.

## Безопасность доставки

Подключение нового контроллера к боту или сайту — **отдельный этап** после
реального теста двух узлов. Нельзя сливать изменения в production без оценки
существующих автоматических deploy workflows и миграций. В этом PR новые
функции остаются неиспользуемыми в живых маршрутах.

Проверки:
- unit tests/node-fanout.test.ts (independent revoke, late ENABLE, unverified
  hard expiry, partial outage, deadline mismatch)
- integration tests/integration/vpn-node-fanout.test.ts (PostgreSQL 0023/0024,
  two-node provisioning, profile publication gates, refund fanout, health)
- regression tests/xray-node.test.ts и остальные Offline code contracts
