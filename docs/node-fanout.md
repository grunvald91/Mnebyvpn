# MNEBYVPN — этап 2: multi-node reconcile, подписки, изолированные ревизии

Дата: 2026-11-07. **CODED; E2E ON REAL NODES NOT VERIFIED; NOT DEPLOYED.**

Этап 2 основан на этапе 1 (PR #43) и не меняет действующий worker или HTTP /sub.

## Главные инварианты

1. **Entitlement revision** отражает права/оплату. Для каждой привязки создана
   независимая **desired_node_revision/applied_node_revision**. Операторское
   отключение узла увеличивает номер сетевой операции даже без изменения оплаты.
   Действующий Xray agent отвергает противоположные действия с тем же номером;
   поэтому disable нельзя отправлять со старой node revision.
2. Отдельный node-side inspect после каждой операции, с проверкой срока,
   нужного состояния, monotonic fencing и CAS. Нет глобального billing ACK.
   Непроверенный timeout — unknown, не подтверждение выданного доступа.
3. Все переходы revoked→pending проходят PostgreSQL admission: блокировка
   строки узла + подсчёт занятых слотов. При переполнении ставится failed
   (node_capacity), оплаченный заказ не отменяется, место не обещается.
4. Специальные узлы требуют allow_special=true на привязке. Provisional trial
   допускает короткий node-enforced 5-минутный срок до основной активации,
   далее требуется новая node revision для 24-часового срока.
5. Draining не принимает новых назначений, но существующие active профили
   остаются в списке подписки до проверенного вывода. Disabled не возвращается
   в список, а его локальный доступ подлежит отдельному отзыву.
6. Генератор подписки отдаёт только действующие по entitlement и per-node
   revision, подтверждённые и проверенные TLS/WS профили. По окончании
   чтения повторно проверяются как право, так и статус узла.

## Не реализовано

- Нет запуска fanout в production, живых probe, настройки нескольких физических
  узлов, контроллера операторских действий и HTTP-выдачи multi-node списка.
- Нет гарантии автоматического переключения клиентов или white-list обхода.
- Нужны E2E hard expiry, physical revoke, shutdown/recovery, DNS/UDP/TCP,
  отсутствие утечек и испытания на Incy/Karing перед включением live.
- Реальный возврат/продление требует отдельного acceptance-test на Xray
  агенте и настоящей БД; синтетические тесты не заменяют физическое испытание.

## CI

Схема 0023→0024, TypeScript, unit, интеграционные проверки с изолированной
PostgreSQL: синхронизация нескольких узлов, возмещение, сбой одного узла,
новый network generation при disable, вместимость, специальный узел,
trial provisional→24h, корректный draining, исключение профиля после
фактического SQL disable. Деплой выполняется только отдельно.
