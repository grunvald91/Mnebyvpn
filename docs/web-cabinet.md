## Обязательный пользовательский сценарий

1. Посетитель видит страницу и **только опубликованные** в `billing_plans` рублёвые тарифы (`enabled=true`, `rub_minor IS NOT NULL`).
2. Выбирает услугу (VPN / Smart DNS / комплект, если комплект когда-либо опубликован), 15/30/60/90 дней. Пустые/неутверждённые варианты недоступны и не имеют вымышленных цен.
3. Открывает `/auth/login` → Telegram OIDC. В BotFather Login Widget необходимо зарегистрировать **реальный** HTTPS-origin и точный callback `https://<домен>/auth/callback`, получить Client ID/Client Secret. Это современный OIDC flow, не устаревший login widget HMAC bot-token.
4. После успешной серверной валидации сайт ставит защищённую сессию на 12 часов. Персональные API никогда не принимают `accountId` от клиента. `GET /api/me` показывает entitlements и заказы того же аккаунта, что обслуживает бот.
5. `POST /api/checkout` только с сессией, Origin и CSRF, планом и уникальным requestId. В существующем `PgBillingStore` PostgreSQL snapshot условий, идемпотентность, rate limit, запрет self-referral и verified capture. Результат — **только** URL Prodamus с allowlist доменов, не обещание оплаченного доступа.
6. Реально оплаченный заказ признаётся `PAID` **только** после подписанного проверенного webhook Продамус, с существующей транзакцией settlement/outbox. `urlSuccess` / возврат браузера не является подтверждением платежа. Продажа цифровых товаров *в Telegram* остаётся на Stars; рублёвый Prodamus используется только на отдельном внешнем сайте.

## Честность квот и сроков

- `expires_at=NULL` означает «ожидает фактической активации», а не вымышленные 24 часа.
- Остаток времени считается из серверного `expires_at` и текущего времени.
- `quota_limit_bytes` показывает размер **предоставленного пакета**. `quota_used_bytes` и «остаток» скрыты, пока `WEB_DNS_METERING_VERIFIED` не был вручную установлен после реального on-wire испытания единого SNI/DoT subscriber bucket на всех узлах/устройствах. Записанные в тестовой БД нули нельзя выдавать за реальные показания.
- Не выдаём под видом работающих кнопок ещё не реализованные VPN профили, private DNS хосты, QR или функции перенастройки клиентов. Выдача конфигураций привязана к будущим реальным provisioning adapters.

**Публичный deployment сейчас блокируется отсутствующими live gates.** Локальный запуск веб-интерфейса возможен только при подготовленной PostgreSQL базе с миграциями 0001–0011 и тестовыми OIDC credentials. Не коммитить секреты или `.env`.

## Этап 13 — оплаченные кредиты и возвраты (только offline)

Миграция `0013_entitlement_credits.sql` вводит FIFO-журнал оплаченных временных
и DNS-квотных кредитов. **Новый тариф не становится новым доступом при продлении**.
Когда возвращён первоначальный платёж, последующие оплаченные продления не
отзываются: удаляется только ещё не израсходованное время возвращаемого
кредита, более поздние оплаченные периоды сдвигаются раньше.

Примеры: первоначальные 30 дней + продление 30 дней, возврат первого платежа
через 10 дней → остаётся 30 дней с момента возврата; первоначальные 30 дней
уже полностью прошли → возврат не уменьшает оплаченное продление.
Возврат будущего продления сдвигает последующие периоды вперёд по очереди.
Счётчик уже учтённых DNS-байтов не уменьшается; лимит не может стать ниже
ранее израсходованных байтов. Сетевой адаптер получает новую revision.

Для надёжной миграции с `0012`: если в базе уже применены оплаченные
продления прежней схемой, миграция **останавливается с ошибкой** — нужна
отдельная сверка операций и ввод начальных записей журнала.

Проверки на реальном платёжном провайдере, маршрутизации VPN/DNS и
сетевых ограничениях **по-прежнему остаются release gates**, поэтому флаги
публичной оплаты не включать до подписанного приёмочного испытания.

### Учёт купленной и уже израсходованной DNS-квоты (0015)

Каждая подтверждённая квота в `entitlement_credits` теперь имеет отдельное
поле `consumed_bytes`. Вызов `debit_smart_dns_quota` распределяет реально
предавторизованные байты между ещё оплаченными кредитами FIFO под одной
блокировкой entitlement; дубли событий не списываются. При возврате одного
заказа из общего остатка убираются только **неизрасходованные байты именно
этого заказа**, а оплаченные остатки других заказов сохраняются. Глобальное
`quota_used_bytes` никогда не уменьшается. Перед применением миграции к БД
с ненулевым историческим расходом требуется подтверждённый backfill — миграция
не пытается выдумывать, на какие заказы приходился этот расход.

Важно: существование корректного SQL-учёта **не доказывает**, что сетевой
прокси/ingress реально выделяет подписке допустимые байты и выполняет этот
атомарный резерв до передачи каждого блока трафика. До такого E2E испытания
`WEB_DNS_METERING_VERIFIED` должен оставаться выключенным.

### Отзыв веб-сессий (0014)

`0014_website_sessions.sql` вводит серверный журнал хешей выданных
браузерных сессий (не сырых cookie). При Telegram OIDC-входе сайт регистрирует
SHA-256 токена в PostgreSQL, каждый персональный запрос проверяет, что
сессия активна и не отозвана, а `POST /api/logout` немедленно помечает её
как отозванную. Токен, ранее выданный, но отсутствующий в БД, получает 401.
Прежние stateless-сессии после миграции потребуют нового входа.

Публичный rate limiting для `/auth/login`, `/auth/callback`,
`/api/checkout`, `/api/renew` и подписанных webhook всё равно должен быть
настроен отдельно в доверенном HTTPS reverse proxy перед выпуском.

### Реальные приёмочные блокировки

SQL/HTTP тесты внутри GitHub Actions используют одноразовую PostgreSQL и
локальный loopback-сервер без участия действующего VPS.
Необходимо отдельно подтвердить: фактическую подпись Prodamus на реальном
уведомлении; запись/продление/возврат у провайдера (включая отдельную
проверку настоящего возврата); Telegram OIDC с реальным клиентом;
действительную выдачу VPN и Smart DNS реквизитов, QR и конфигураций,
проверку hard-expiry без панели и общий on-wire DNS расход с отсечением
по квоте; юридические реквизиты, тарифы и условия, поддержку пользователей.
Не включать продажи по одной только успешной CI.

## Этап 20 — вход по email с кодом и Telegram (06.11.2026)

**Актуальная схема.** Яндекс OAuth для MNEBYVPN отключён. Черновик ServGo
PR #146 по Яндексу закрыт; почтовая интеграция — ServGo PR #147.
Главный вход на сайте: email → шестизначный код на email →
`POST /api/auth/email/verify` → одна серверная сессия в `accounts.id`.

### Почта и сервисная инфраструктура

- Отправитель: строго `mnebyvpn@servgo.ru`, бренд `MNEBYVPN` латиницей.
- Письмо отправляется через **существующую почтовую систему ServGo**:
  `POST https://servgo.ru/api/auth/mnebyvpn/email-code`, который вызывает
  `bot.services.email_notifications.send_email` с безопасным override From.
  Рабочий SMTP-пароль **не** хранится в MNEBYVPN.
- Серверный вызов требует `MNEBYVPN_MAIL_GATEWAY_SECRET` длиной минимум
  32 символа с **одинаковым значением** на обеих сторонах, HMAC-SHA256
  над timestamp, nonce и точным телом JSON, TTL 60 секунд, атомарное
  одноразовое использование nonce через PostgreSQL в ServGo.
- Код 6 цифр, TTL 10 минут, один успешный вход, максимум 5 неверных
  проверок; запрос нового кода не чаще раза в 60 секунд, максимум 5
  email-запросов в час на адрес и 80 в час на сетевой IP (снижение abuse;
  IP мобильных провайдеров могут быть общими).
- В MNEBYVPN хранится только HMAC-хеш кода, не сам код. Новая авторизация
  по email не требует пароля и не зависит от Telegram.
- `WEB_EMAIL_LOGIN_ENABLED=yes` включать только **после** миграции
  `db/migrations/0101_email_otp_and_trial_devices.sql`, проверки SMTP From,
  SPF/DKIM/DMARC и установки секретов. Маршрут ServGo требует миграции
  `migrations/add_mnebyvpn_email_gateway.sql` до включения.
  Перед выпуском проверить что nginx ServGo маршрутизирует точный путь на API.

### Telegram — второй вход

- Telegram подтверждается **официальным Telegram Login/OIDC**
  (BotFather OAuth Client ID/Secret и зарегистрированный callback), не
  отправкой нашего ботом кодов.
- После email-входа доступна явная привязка через `/auth/login?link=1`.
  Если Telegram ID уже принадлежит другому `accounts.id`, автоматического
  слияния платежей и trial **нет**: требуется проверка владельца/ручное
  разбирательство.
- Прямой вход через Telegram разрешён для **ранее привязанных** либо
  уже существующих в Telegram-боте аккаунтов. Незнакомый Telegram ID
  перенаправляется на email-вход, без создания нового trial аккаунта.
- `WEB_TELEGRAM_OIDC_ENABLED=yes` включать только с действующими
  BotFather credentials. В сетях, где Telegram недоступен, работает
  email-вход через ServGo.

### Пробный VPN и ограничения антифрода

- `POST /api/trial` — только после email/Telegram авторизации, с CSRF.
- На первом GET страницы выставляется `__Host-mnebyvpn_device` — случайный
  HttpOnly Secure cookie. Сохраняется **только SHA-256-хеш** токена.
- `trial_grants.account_id UNIQUE` даёт не более одного trial на
  внутренний аккаунт. `trial_device_claims.device_hash PRIMARY KEY`
  резервируется **в одной транзакции с пробной подпиской**: другой аккаунт
  из того же браузера получает `DEVICE_ALREADY_USED`.
- Важно: очистка cookies, другое приложение/браузер, смена телефона
  или имитация HTTP-клиента **обходят браузерную привязку**. Ни email,
  ни Telegram, ни сайт не дают неподлежащее подделке подтверждение
  «один физический телефон = одни сутки». Требование пользователя выполняется
  лишь как *best effort*. IP нельзя использовать как абсолютный
  идентификатор телефона (особенно CGNAT у мобильных операторов).
- Telegram-бот использует тот же уникальный `accounts.telegram_user_id`
  и `trial_grants.account_id`, но **связать пробную выдачу в боте с
  неизвестным email без связывания аккаунтов нельзя**.
- Начало срока — только после узлового ACK; существующие VPN-подписки,
  DNS и оплаченные заказы не обнулять.
