# ADR-0006 — Совместимость Smart DNS + VPN, приватность, скорость и географический выход

Дата: 2026-11-06. **Решение по требованиям продукта принято; реализация и E2E-совместимость UNVERIFIED.** Это документация, не разрешение изменять действующие VPS/прокси.

## Цель и приоритеты

Системный Android Private DNS (настроенный один раз через hostname DNS-over-TLS) и наш VPN должны **по возможности работать совместно, без необходимости ручной смены DNS при включении/выключении VPN**. Оптимизируем одновременно:

1. Защиту DNS и содержимого соединений, отсутствие незаявленных утечек и отказ от TLS MITM.
2. Производительность: минимальные дополнительные переходы, разумные задержки, стабильность связи и расход батареи.
3. Доступность разрешённых сервисов, ограничивающих подключения по стране исходящего IP, за счёт подходящего **зарубежного egress** — без обещаний гарантированного обхода каждой географической/сетевой блокировки.

Принцип: **security/privacy by default, performance by measurement, geo-exit by explicit verified policy**. Нельзя подменять «private DNS» понятием «шифрование всего интернета».

## Границы гарантий и модель угроз

- **DNS-over-TLS** шифрует только DNS-запросы/ответы между устройством и DNS-сервером. IP назначения и иные метаданные могут оставаться видимыми; приложения могут использовать собственный DNS.
- **VPN-туннель** защищает трафик между устройством и VPN-узлом от наблюдателя на этом участке, но **на выходе VPN-узла** действуют правила конечного протокола: HTTPS/TLS обычно защищён до исходного сервера, HTTP без TLS не становится end-to-end защищённым.
- **Smart DNS + разрешённый SNI/TCP passthrough** может отправлять HTTPS трафик к origin через зарубежный ingress с сохранением исходной TLS-сессии без расшифровки нами. Для *обычных* DNS-only доменов трафик идёт напрямую, а реальный IP клиента **не скрывается**. TCP SNI-proxy не является полноценным VPN.
- Географический контроль может проверять не только выходной IP, но и учётную запись, платёжный регион, GPS, cookies/отпечаток браузера, ASN/репутацию адреса. **Не гарантируем** доступ при любых ограничениях.
- Полная анонимность/«невозможность расшифровать вообще» не обещаются: VPN-оператор видит часть метаданных, origin знает содержимое, которое ему отправляет приложение, а небезопасный HTTP остаётся небезопасным после выхода.
- Если ECH/HTTP3/QUIC не поддерживаются SNI-путём, **не ослаблять TLS, не отключать проверку сертификатов и не устанавливать root CA** ради успешного подключения. Домен исключается из SNI-маршрута до проверки.

## Политика трёх путей

| Путь | DNS | Исходящий IP, видимый сайту | Цена для приватности/скорости |
|---|---|---|---|
| **A. Private DNS only** | DoT с валидным TLS именем | Обычный IP подключения | Минимум обработки; DNS скрыт от локального пассивного наблюдателя, остальное не туннелируется |
| **B. Private DNS + Smart SNI** | DoT, только проверенные домены переписываются на авторизованный SNI ingress | Для проксируемых доменов — IP egress; для прочих — обычный IP | Выборочная проксизация TCP HTTPS; ограничения ECH/QUIC/IPv6/DNSSEC; платный SNI пока BLOCKED |
| **C. Private DNS + наш VPN** | Предпочтительно тот же пользовательский DoT hostname, доступный через VPN; фактический DNS-маршрут определяется клиентом и проверяется | VPN egress для трафика, реально прошедшего туннель | Защита всего направленного в туннель трафика до узла, но возможны задержки/нагрузка и клиентские особенности |

Android Private DNS + любой конкретный VPN-клиент — **не гарантированная комбинация на уровне ОС**. VPN может управлять DNS, маршрутизацией, исключениями приложений и перехватом; матрица зависит от версии Android, производителя, клиента, профиля VPN и сети. Совместное размещение сервисов на **одном VPS — удобный кандидат, но само по себе не обеспечивает совместимость**. Размещать их вместе только после проверки портов, ресурсов, изоляции и конфликтов на текущих серверах.

### Сценарий «VPN выключен → включён → выключен»

1. **VPN выключен:** Android использует настроенный DoT hostname при наличии поддержки; MNEBYDNS применяет правила выбранного DNS-профиля.
2. **VPN включён:** проверяем, действительно ли Android/клиент продолжает делать DNS-запросы в наш шифрованный resolver через ожидаемый путь. Если клиент принудительно использует другой DNS, это обнаруживаем в испытании и явно документируем совместимость/ограничение; не обещаем автоматического сохранения Private DNS без теста.
3. **Оптимизация внутри собственного VPN:** при доступной доверенной идентификации VPN-контекста resolver может выдавать обычные origin DNS-ответы для доменов, которые уже выходят через зарубежный VPN egress, чтобы исключить бессмысленную цепочку VPN → тот же SNI ingress → origin. **Не определять VPN-контекст по одному легко подделываемому признаку**. Допустим отдельный внутритуннельный resolver с идентичной DNS-политикой, если системный Private DNS и конкретный клиент конфликтуют; изменение пользовательской настройки допускается только как явно описанная несовместимость, а не скрытый fallback.
4. **VPN выключен снова:** тот же системный DoT hostname должен работать без ручных действий на протестированных конфигурациях, после смены сетей и при кешированных DNS ответах.
5. Никаких DNS-петель или hairpin двойного проксирования; закрытый внутренний DNS порт не должен становиться публичным open resolver.

## Режимы баланса (проектное предложение, не реализованный переключатель)

- **Сбалансированный (кандидат по умолчанию):** проверенный защищённый DNS, TLS до origin, VPN при явном включении; минимизируем двойные переходы; автоматический выбор egress **только** из разрешённых/проверенных узлов и по понятному правилу. DNS-only не выдаём за защиту всего трафика.
- **Максимальная приватность (явный выбор):** полный VPN-туннель для поддерживаемых IP-семейств, защита от утечек, запрет незаявленного direct fallback; опция Android Always-on VPN + «Блокировать подключения без VPN» (если доступна в данной конфигурации). Сбой защищённого DNS/туннеля — блокировать затронутые подключения, а не переводить незаметно на незащищённый DNS/direct.
- **Выборочная маршрутизация (явный выбор):** региональные сервисы напрямую, необходимые географически ограниченные — через подтверждённый egress. Указать пользователю, что прямые соединения раскрывают реальный IP и не защищены VPN. Split tunneling зависит от клиента, маршрутов, приложения и DNS.
- **Недоступный по географии сервис:** не пытаться «лечить» только DNS-ответом. Проверять IP видимый origin и выходную страну, доступность/репутацию конкретного узла, при необходимости предлагать другой проверенный egress. Системные проверки сайта могут по-прежнему отказывать.

Не навязывать более медленный «два слоя VPN» как якобы более безопасный стандарт. Дополнительное шифрование DoT поверх VPN допустимо и не тождественно вложенному VPN-туннелю.

## Правила приватности и эксплуатации

- DoT с проверкой имени и действующего сертификата. Не отключать TLS validation и не переходить автоматически на открытый DNS при строгом режиме.
- Для VPN — подтверждённая проверка IPv4/IPv6/DNS/UDP/QUIC, отключение bypass там, где пользователь ожидает full tunnel, и испытания при смене сети/сне.
- Сохранять HTTPS/TLS до origin; без MITM и без установки CA на клиенте. Не ухудшать поддержку безопасных возможностей (ECH, TLS 1.3) ради несовместимого SNI маршрута.
- Предпочитать агрегированные метрики. Не вести постоянную per-domain историю запросов, не сохранять пользовательский payload; минимальные оперативные данные, ограничение сроков хранения, контроль доступа, защита backup и журналов. Конкретные сроки retention утвердить перед production.
- DNS resolver и SNI ingress должны иметь независимую авторизацию, rate limits и ACL; нельзя связывать TCP поток с подпиской лишь по DoH токену. **Paid SNI остается BLOCKED** до доказательства per-flow attribution и server-side quota.
- В единой подписке VPN+DNS избегать **двойного списания одного и того же потока** при прохождении DNS, VPN и SNI; метрики сервисов не автоматически суммируются в одну квоту. Решение о коммерческом учёте требует отдельного утверждения контракта.

## E2E проверка до обещаний клиентам

Матрица: актуальные версии Android и разные производители; системный Private DNS с фиксированным hostname; наши и сторонние поддерживаемые VPN-приложения (Happ/INCY/v2rayNG/Karing по фактической доступности); Wi-Fi/мобильная сеть; VPN off → on → off; перезапуск/сон; IPv4, IPv6, UDP/QUIC, встроенный DoH приложения.

Проверить с документированными обезличенными результатами:

1. Сохраняется ли зашифрованный DoT и какой resolver реально обслуживает запросы; нет ли plain DNS утечек/невидимого fallback.
2. В full-tunnel режиме: DNS leak, IPv6 leak, IP выхода и WebRTC (где применимо), поведение при падении узла/туннеля, отсутствие скрытого direct.
3. В выборочном режиме: какие приложения/домены идут напрямую; соответствует ли реальный egress ожидаемой стране, нет ли ошибочного обещания «скрываем всё».
4. SNI passthrough: валидный сертификат origin, запрет TLS MITM, отсутствие loops и двойных ingress-hop при VPN. ECH, QUIC и DNSSEC — отрицательные тесты.
5. Цифровые показатели **относительно baseline на той же сети и устройстве**: медиана и p95 задержки DNS, время установления TLS, throughput, packet loss, стабильность, расход батареи/CPU, стоимость трафика на узле. Пороговые значения утверждаются **после замеров**, цифры заранее не выдумывать.
6. Внешняя проверка географической доступности через выбранный egress; фиксировать причины отказа (IP/ASN, учётная запись, ограничения сайта). Гарантий успеха нет.
7. Отдельный контроль действующих VPS, port map и восстановимость; никаких изменений на сервере без согласования.

**Release gate:** пока клиентские и сетевые испытания не пройдены, совместимость «Private DNS + VPN без переключений», отсутствие DNS утечек и географическая доступность имеют статус **UNVERIFIED**. До коммерческого релиза нужны тесты и безопасный план отката.
