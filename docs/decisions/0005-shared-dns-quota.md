# ADR-0005 — общий трафик одной подписки, любое количество устройств

Дата: 2026-11-05. **Бизнес-модель определена, работающий механизм учёта пока не создан.**

## Решение

Мы продаём клиенту **пакет трафика MNEBYDNS**, а не разрешение на конкретное устройство. Владелец подписки вправе использовать один профиль на телефоне, планшете, ПК и передавать другим людям. Нет HWID, лимита устройств и требования определять человека по source IP. Все подключения по профилю тратят единый `quota_limit_bytes`; после исчерпания нужно купить дополнительный пакет/продлить.

**DNS-запросы и трафик HTTPS — не одно и то же.** Персональный DoH URL позволяет проверить право на DNS-ответы, но после DNS-ответа клиент устанавливает независимый TLS/TCP поток к proxy ingress. DoH-токен сам туда не передаётся. Чтобы продавать *гигабайты проксируемого трафика*, ingress обязан относить каждый входящий поток к `subscription_id`.

## Кандидат реализации: уникальный адрес ingress назначения

- Для каждой оплаченной подписки — один уникальный защищённый DNS URL и **отдельный destination IPv6** из префикса, если хостер реально маршрутизирует выделенные IPv6 и клиенты способны до них подключаться.
- DNS выдаёт принадлежащий подписке IP ingress; ingress по **destination IP**, а не source IP, относит поток к общей квоте. Все устройства могут использовать тот же адрес и расходуют общую квоту.
- Destination IP — **передаваемое право доступа (bearer credential)**. По нему нельзя удостоверить личность. Если его узнали посторонние, они могут расходовать чужую квоту. Это коммерческий риск, который нужно оценить; не обещаем защиты от использования чужого IP.
- Если нет выделенного IPv6 или поддержка IPv6 в целевых сетях недостаточна, модель не универсальна. Возможная альтернатива — **явный авторизованный прокси** с токеном или другая протокольная маркировка потока. Уникальный путь DoH без ingress attribution НЕ решает задачу.
- Неиспользуемые IP закрыты; reuse адреса между подписками — только после завершения сессий и учёта DNS кеша/TTL, чтобы не отдать чужой трафик новой подписке.

## Реальный учёт и исчерпание

Параметры: `subscription_id`, `expires_at`, `quota_limit_bytes`, `quota_used_bytes`, `quota_state`, `entitlement_revision`. По договорной политике определить, считать ли входящие+исходящие байты, накладные расходы, ответы с ошибками, точность и допустимое превышение.

- Любое новое соединение сверяет `quota_state` и маршрут назначения; `EXHAUSTED` → DENY, даже при сохранённом IP и DNS кеше.
- Для жесткой квоты текущие соединения должны получить лимит/разрыв, а счётчик **атомарно** учитывать одновременные потоки. Логи только по завершённым соединениям не гарантируют hard cap.
- При нескольких входных серверах нужна общая согласованная квота или безопасные распределённые предвыделенные лимиты, чтобы конкуренция не дала безлимитный расход.
- Refund/expiry/revoke меняют `revision` и отключают *весь* пакет, поздние выдачи не должны возвращать доступ.

## E2E до продажи

1. Два-три устройства используют одну подписку с разными исходными IP и сетями. Счётчик единый.
2. После исчерпания пакета новое соединение с любого устройства запрещено, включая прямой IP без свежего DNS-запроса.
3. Старые длинные TCP соединения остановлены согласно измеренному максимальному overshoot.
4. Неиспользуемые IP + чужой SNI не дают бесплатного маршрута; известный персональный IP потенциально может сжигать чужую квоту, риск отражён в условиях продукта.
5. Проверить реальные IPv6 маршруты провайдера, IPv4-only сеть, DNS ECH/QUIC и механизм fallback.
6. Параллельные соединения и два ingress узла не расходуют больше установленных лимитов сверх утвержденной погрешности.
7. Продление/пополнение квоты и отзыв доступа не ломаются от повторных платежей и задержанных задач.

**До пройденного PoC продукт платного SNI traffic остаётся BLOCKED.** Никакой установки на текущие VPS этим ADR не разрешается.
