# MNEBYVPN — расширяемый реестр VPN-узлов (первый этап)

Дата: 2026-11-07. **CODED / E2E BLOCKED. Не включено в runtime.**
Количество узлов не ограничено константой «10», однако масштабирование на практике зависит
от БД, политики размещения, сетевых ресурсов и испытаний.

## Реализовано в отдельном слое

- Миграция 0023: каталог vpn_nodes и привязки vpn_node_assignments с отдельными
  desired_revision / applied_revision, без хранения секретов или VLESS-ключей.
- packages/nodes/src/registry.ts: жизненный цикл и отбор кандидатов.
  Условия: verified, ручной допуск, свежий успешный health, подходящий протокол,
  доступная ёмкость; special — только по отдельному разрешению.
- packages/nodes/src/pg-registry.ts: регистрация узла только как planned,
  сохранение результата внутреннего health-probe, чтение кандидатов, транзакционная
  бронь места с блокировкой строки узла. Все брони получают статус pending.
- SignedXrayNodeApi: отдельно переданные контрольный адрес и клиентский WSS-маршрут.
  Без новых параметров сохраняет исходный маршрут, поэтому действующий worker/бот
  не меняют поведение.

## Пока НЕ реализовано

- Нет endpoint управления, автозакупки VPS, autopromotion verified,
  автоматического распределения, балансировщика и drain.
- Нет multi-node fanout provisioning/revoke, независимого подтверждения выдачи
  на каждом узле, производственного health-probe или подтверждённого auto-failover.
- vpn_node_assignments.pending — намерение для будущего worker, не право доступа
  и не основание показывать сервер клиенту. Текущий одиночный data plane не меняется.
- SQL CHECK для отметки одобрения и отпечатка E2E-отчёта не доказывает фактическое
  проведение тестов: требуется отдельный подписанный отчёт.

## Для подключения следующего узла

1. Изолированно настроить узел без изменений действующей сети; проверить HMAC control
   и WSS-клиентский путь.
2. Зарегистрировать как planned, пройти testing -> canary и проверить
   трафик, DNS/UDP/TCP, нагрузку, отзыв доступа без панели.
3. Оператор после проверки E2E-отчёта допускает verified. Внутренний
   аутентифицированный health-probe должен давать свежие результаты.
4. Реализовать per-node dispatcher с CAS revision, hard expiry и fanout revoke.
   Публиковать профиль только после успешной проверенной выдачи прав на узле.
5. Реализовать единую подписку с несколькими профилями и испытать обновление /
   переключение на конкретных клиентах.
6. Миграцию production проводить отдельно, после backup, canary и rollback.

## Проверки

- Unit: tests/node-registry.test.ts — фильтры и недопустимые переходы.
- Integration: tests/integration/vpn-node-registry.test.ts — бронь, отказ,
  статус pending, ёмкость и недоступность после failed probe.
- Regression: tests/xray-node.test.ts — прежний URL и новый независимый маршрут.

Не изменяются nginx, DNS, firewall, действующий Xray, production DB и подключения.
Статус CI подтверждается отдельно в PR.
