# Безопасность, лицензии и данные

Публичный репозиторий — только архитектура и обезличенные шаблоны.

## Угрозы

1. Утечка subscription URL/UUID/ключей: URL подписки и QR считать секретом уровня доступа; маскировать в логах и UI поддержки.
2. Компрометация Remnawave API/admin: отдельный токен с минимальными правами (если upstream позволяет), ограничение сетевого доступа, аудит действий.
3. Подделка оплаты: проверка подлинности webhook **и** актуального статуса у провайдера, уникальность event ID, транзакционный outbox.
4. Повторный webhook / сбой API: повтор операции не должен давать дополнительных дней или оставлять неограниченный доступ.
5. Неисполненный revoke: регулярная сверка прав из MNEBYVPN с Remnawave и принудительное отключение на действующем data plane.
6. Утечка данных клиента: минимизация собираемых идентификаторов, TTL, контроль доступа, политика хранения и удаления.
7. Ложная безопасность из-за HWID: HWID клиента не универсален, не доверять для всех ОС и не считать криптографическим доказательством личности.
8. Зависимость от двух VPS: резервные копии вне узлов, процедура переноса подписочного endpoint и проверка восстановления.
9. Публичность `telegram-proxy-infra`: наличие адресов/санитизированных схем в истории требует отдельного аудита и гигиены секретов.

## Безопасность деплоя

- Не копировать приватные ключи/пароли/real `.env` в GitHub. Использовать секреты окружений и существующую защищённую инфраструктуру.
- Production и staging изолированы на уровне конфигурации, токенов, БД и пользователей.
- Образы pinned, обновления только с preflight/тестами и rollback.
- Admin endpoints не выставлять публично без необходимости и защиты.
- Не публиковать логи авторизации, proxy share links и полные URL подписок в Actions.
- Бэкапы — зашифрованные, вне VPS, с контролем доступа и тестом восстановления.
- Проверить применимость российских норм к обработке персональных данных/оплате перед продажами; юридическое заключение отсутствует.
