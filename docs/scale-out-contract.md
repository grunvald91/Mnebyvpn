# P1 — автомасштабирование: реальная нагрузка и бюджетная транзакция

Дата: 2026-11-05. **СТАТУС: SPEC / AUTOSCALING DISABLED.** Созданный VPS **не равен** разгруженному сервису.

## Scale-out: распределение работы

1. Событие требует реальной перегрузки **и деградации подключения**, подтверждённых независимыми измерениями. Блокировка со стороны оператора не лечится созданием новых VPS по одному CPU сигналу.
2. Provisioner создаёт новый узел; проверяет версии, auth, health, сетевой профиль, непрерывную безопасность, бэкап/rollback. Узел = `testing`, не публичный.
3. Canary-тест из нужных сетей, затем публикация только в подходящие группы Remnawave subscriptions.
4. **Новые пользователи:** назначаются контроллером размещения согласно подтверждённой емкости/региону/протоколу/стоимости; affinity/pinning пользователя к исходному узлу — по тарифной политике.
5. **Уже подключённые пользователи:** могут продолжить использовать старый узел до ручного переключения или обновления подписки. Механизм смены сервера и auto-update **доказывается отдельно по клиенту**. Принудительная миграция без работающего клиентского механизма не объявляется доступной.
6. Планировать drain старого узла только с измеренным процентом мигрировавших соединений; не отключать перегруженный сервер ради «перераспределения», если клиенты не переключились.
7. Успех масштабирования = p95/p99 времени соединения, коэффициент успешных подключений, CPU/connection/bandwidth на исходном узле, throughput новых пользователей, фактическое перераспределение, отсутствие роста ошибок. Просто «сервер добавлен в Base64» — НЕ PASS.

## Состояния

`CapacityIncident` → `ScaleProposal` → `BudgetReservation` → `Provisioning` → `UnknownOutcome | Created` → `Bootstrapping` → `Healthy` → `Canary` → `EnabledForNew` → `ObservedRelief`; при провале `Quarantined`/ручной разбор.

Планировщик **не должен** автоматически отключать/удалять платный узел без подтверждённого drain и корректного биллинга провайдера.

## Атомарный учёт денег

- В одной сериализуемой транзакции или строгой блокировке `(billing_account, budget_period)`: рассчитать `already_committed + reservations + worst_case_new_cost <= hard_cap`; если неизвестна стоимость или валюта/период тарификации — DENY.
- `already_committed` включает созданные, ещё не активированные, деградировавшие, удаляемые, **с неизвестным фактом удаления** и текущие месячные обязательства; `reservations` — pending create/resize включая конкурирующие регионы и контроллеры.
- Резерв создаётся **до** первого API create и журналируется с `resource_request_id`, provider/account/region/plan, цена и срок обязательства. Деньги не освобождаются по timeout API.
- Предпочесть provider idempotency key и метку/тег `managed_by=MNEBYVPN`, `request_id` (без персональных данных); перед повтором проверять provider inventory.
- `UnknownOutcome`: не повторять create. Сначала запросить provider list/get, сравнить request_id/документированный correlation ID, установить точное состояние и расходы; если provider не даёт однозначной идентификации — **ручная разборка**, резерв остаётся.
- `Created` фиксирует provider resource ID, цена/расход, ожидаемый billing cycle; periodic inventory reconciliation выявляет «осиротевшие» VPS и продолжает их учитывать в бюджете.
- Уменьшение бюджета учитывает уже созданные обязательства; превышение hard cap → запрет новых действий + алерт, **не автоматическое удаление VPS**.

## Тесты

1. Две конкурентные заявки из разных регионов при остатке бюджета на один узел → ровно одна reservation.
2. Provider создал сервер, ответ потерялся → reconciliation находит один ресурс, второй не создаётся.
3. Created, но не прошёл health → всё ещё учитывается в расходах.
4. Delete API завершился неопределённо → сервер учитывается до подтверждённого отсутствия/окончания биллинга.
5. Новый узел healthy и подписка обновилась, но старые клиенты на прежнем узле → масштабирование **не считать успешным**, нужен план перехода.
6. Сетевые ограничения без CPU saturation → не делать ложный scale out.

`special` nodes и незнакомые провайдеры — manual approval по умолчанию. Контракты выбора provider/API и реальные цены пока отсутствуют.
