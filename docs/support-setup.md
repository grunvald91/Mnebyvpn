# MNEBYVPN — поддержка через основной Telegram-бот

## Один бот для всего

Для подписок, обращений пользователей и ответов оператора используется только [@MnebyVPN_bot](https://t.me/MnebyVPN_bot). Отдельный операторский чат/группа и `SUPPORT_TELEGRAM_CHAT_ID` **не нужны**.

- Пользователь в боте нажимает «✉️ Поддержка» или пишет `/support`. Ответ на приглашение либо `/support <вопрос>` передаётся личным сообщением оператору **от этого же бота**.
- Оператор открывает свой обычный личный диалог с MNEBYVPN и нажимает **«Ответить» на уведомление клиента**. Бот сверяет Telegram user ID отправителя и private chat ID с одним настроенным ID оператора. Ответ пересылается клиенту через Bot API, после подтверждения API оператор получает отметку.
- Операторские команды `/start`, `/my`, `/plans` не блокируются: тот же аккаунт может пользоваться обычным ботом.
- Обращение с сайта также приходит оператору в тот же диалог. Если посетитель не входил через Telegram, то его Telegram ID неизвестен. Поэтому ответ оператора, написанный через **Reply в том же боте**, сохраняется в сайт-тикете. Посетитель видит его в браузере, где отправил форму.

## Приватная конфигурация

Обеим backend-службам нужен **тот же Bot API token, который уже используется для MNEBYVPN**. В GitHub Actions существующий секрет называется `TELEGRAM_TOKEN_BOT`. При запуске поддержки его надо безопасно передать в закрытое окружение веб-сервера и основного webhook backend (не публиковать в репозитории).

| Переменная среды | Значение |
|---|---|
| `TELEGRAM_TOKEN_BOT` | Секрет токена существующего `@MnebyVPN_bot`; это **не второй бот** |
| `SUPPORT_TELEGRAM_OPERATOR_ID` | Личный числовой Telegram user ID владельца, найденный в предыдущей переписке; его значение вводится только в **приватной конфигурации** |

**Других Telegram ID и отдельных chat ID не требуется.** Для личной беседы Bot API использует user ID оператора как destination `chat_id` автоматически. Оператор должен хотя бы раз открыть диалог с ботом и нажать Start, иначе Bot API не сможет инициировать переписку.

Публичная ветка не содержит настоящих значений секрета или персонального ID владельца. Текущие production-файлы окружения не изменялись в этом PR: **пока переменные не настроены, реальная отправка будет выключена**. Имеющаяся архитектура ранее держала Bot API token только в GitHub Actions, а не на VPS; перенос токена в runtime требует проверки разрешений, защиты секретов и ротации. Нет основания объявлять функцию работающей на production до проверки.

## Сайт и ответы

- Без обязательного входа: `POST /api/support` принимает контакт (email / Telegram username), сообщение и пустое honeypot-поле.
- На сервере создаётся UUID обращения и случайный 32-байтовый bearer-токен, хешируемый SHA-256 в БД. Посетителю устанавливается `HttpOnly`, `SameSite=Lax` cookie с токеном, `Secure` на HTTPS, срок 30 дней.
- Уведомление от **того же бота** отправляется оператору с `Заявка: <UUID>`. Ответ владельца на уведомление сохраняется внутренним вызовом `POST http://127.0.0.1:<WEB_PORT>/api/support/operator-reply`, подписанным HMAC-SHA-256 от общего Bot API token. Этот маршрут не принимает ответы без правильной подписи.
- Браузер проверяет `GET /api/support/ticket` с приватной cookie. Угадать UUID недостаточно: без случайного токена ответ не открывается. Ответ отображается через `textContent`, а не как HTML.
- Миграция: `db/migrations/0018_website_support_tickets.sql`. Нужна проверка развертывания миграции **до включения формы**.
- Веб-порт при ответе оператора читается из `WEB_PORT`, по умолчанию 8791. Бот сначала пробует локальный веб-процесс (`127.0.0.1`), а если его нет — фиксированный публичный HTTPS-origin `https://mnebyvpn.site`. Оба пути требуют HMAC; произвольный URL из сообщения пользователя никогда не используется. Доступность обоих путей требует сетевой E2E-проверки.

## Ограничения и защита

- Отправка подтверждена, только если Telegram Bot API вернул `ok: true`. Это **не означает**, что оператор уже прочитал сообщение.
- При сетевом таймауте доставка может быть неопределённой, возможны повторы. Дедупликация обновлений Telegram в памяти, после перезапуска не гарантируется. Для SLA потребуется durable outbox.
- Простейший rate limit — в памяти одного процесса: 3 запроса на контакт или Telegram ID за 15 минут и глобально 120/мин. Он не заменяет edge rate limiting и антиспам.
- `website_support_tickets` хранит контакт, вопрос, ответ. Установлена автоматическая очистка записей старше 30 дней (при запуске веб-сервера и каждые 6 часов). Перед публичным запуском необходимо юридически подтвердить обработку персональных данных, права доступа и соответствие такого срока опубликованной политике.
- Для клиента на сайте одновременно доступно одно последнее обращение с этого браузера: новый тикет заменяет cookie предыдущего.
- Не обещать скорость ответа «N минут», пока она реально не обеспечена.
- Не просить пароли, коды входа, приватные ссылки подписок.

## Проверки до выпуска

1. Выполнить миграцию 0018 на тестовой базе, запустить unit + integration + TypeScript проверки.
2. Проверить в приватной среде правильный основной токен и ID оператора, отсутствие утечек в логи, доступность localhost-bridge.
3. Бот: пользователь → владелец → ответ клиенту; чужой отправитель и группа должны быть отклонены. Владелец должен по-прежнему иметь доступ к обычному меню.
4. Сайт: форма без входа → уведомление владельцу → Reply в боте → ответ посетителю на сайте. Неавторизованное чтение ticket и неверная HMAC-подпись должны быть отклонены.
5. Проверить обработку дубликатов, таймаутов, перезапусков и отсутствие ложного статуса доставки.
6. Коммерческие gates остаются определёнными `docs/release-gates.md`; PR сам по себе не разрешает запуск.

Документация Bot API: https://core.telegram.org/bots/api#sendmessage и https://core.telegram.org/bots/api#making-requests-when-getting-updates .
