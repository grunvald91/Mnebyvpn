# Доверенный контроллер FI: локальная подготовка ключей (этап 1)

**Статус: только код установки и проверок для существующего сервера 188.** В production-контроллере ничего
не запущено, FI-узел не зарегистрирован и клиентские ссылки не включены.

Основной для существующего RU188 установщик: `ops/controller188-key-bootstrap.py`
(Python 3 + уже установленный OpenSSL/OpenSSH). Прежний
`ops/trusted-controller-bootstrap.mjs` остаётся проверяемой Node.js-реализацией
для других подготовленных сред, но на 188 нет `node` на хосте.
Установка выполняется **только на существующем центральном сервере RU188**
(`188.120.254.223`), где уже работают сайт, Telegram-бот, PostgreSQL и VPN-worker.
Новый контроллер не создаём. Приватные подписывающие ключи держать отдельно
в `/root/mnebyvpn-controller`: веб-сервер, бот и обычные worker-процессы
не должны иметь доступа к этому каталогу. Не запускать установку на
FI/DE89 или в GitHub Actions.

## Одноразовая локальная подготовка

На **сервере 188**, после read-only аудита существующих процессов и проверки исходного кода из `main`:

```bash
sudo python3 ops/controller188-key-bootstrap.py init
```

Скрипт создаёт в `/root/mnebyvpn-controller/`:

| Файл | Назначение |
|---|---|
| `controller-signing-key.pem` | Приватный Ed25519-ключ контроллера (0600). Никогда не экспортировать |
| `controller-public.spki` | Публичный 44-байтный Ed25519 SPKI |
| `fi-enrollment-ssh` | Отдельный приватный SSH-ключ регистрации FI (0600). Никогда не экспортировать |
| `fi-enrollment-ssh.pub` | Публичный SSH-ключ для ограниченной `authorized_keys` на FI |
| `bootstrap-manifest.json` | Учёт **неутверждённой** локальной подготовки; не является разрешением |

Каталог имеет доступ только root. Скрипт отказывается заменять уже
существующий каталог, чтобы повторный запуск не сменил ключи и не оборвал
связь. Ключи в командную строку, GitHub или журналы не выводятся.

**Важно:** контрольная сумма `controller_public_sha256` при создании
ключа — это только факт генерации. Она **не** подтверждает независимое
одобрение публичного ключа. Оператор сверяет публичный SPKI по отдельно
утверждённому каналу, фиксирует его SHA256 вне этого процесса.

## Переход к проверке доверия

После независимого подтверждения публичного SPKI задайте его SHA256 при
аудите, например:

```bash
sudo python3 ops/controller188-key-bootstrap.py audit \
  --approved-controller-sha256 <ПРОВЕРЕННЫЙ_SHA256>
```

Аудит проверяет соответствие private/public Ed25519, пары SSH-ключей и
наличие защищённых файлов. Отсутствующая доверенная запись FI SSH
`known_hosts` или заранее утверждённый FI SPKI **не** заменяются новым
ключом или результатом `ssh-keyscan`.

Для проверки конкретно SSH-хоста оператор независимо подтверждает
реальный публичный SSH-ключ FI и его fingerprint `SHA256:...`, затем
сохраняет **ровно одну** запись `fi.mnebyvpn.site ssh-ed25519 ...`
в `/root/mnebyvpn-controller/fi-known_hosts` (root:root 0600).
Это фиксированный `HostKeyAlias`, а не адрес подключённой среды.
Никакого `StrictHostKeyChecking=accept-new`.

Публичный Ed25519 SPKI **самого FI-узла** (44 байта) хранится в
`/root/mnebyvpn-controller/fi-node-public.spki` (root:root 0600).
Код сверяет его SHA256 со значением из проверенного
`nodekit/fleet/fi.json`; скачивание ключа из непроверенного SSH
само по себе не подтверждает идентичность сервера.

После независимой проверки обоих файлов:

```bash
sudo node ops/trusted-controller-bootstrap.mjs audit \
  --approved-controller-sha256 <ПРОВЕРЕННЫЙ_SHA256_SPKI> \
  --approved-fi-host-sha256 <ПРОВЕРЕННЫЙ_SSH_SHA256>
```

Даже успешное `local_ssh_enrollment_material_ready=true` **не**
означает, что применены миграции PostgreSQL 0128/0129, одобрена запись
`vpn_node_enrollment_inventory`, установлены публичные ключи на FI или
получен одноразовый ответ. Скрипт **не** создаёт/меняет записи БД,
не открывает порты, не создаёт клиентские права и не запускает воркеры.

## Следующая отдельная операция

1. Передать на FI **только** `controller-public.spki` и
   `fi-enrollment-ssh.pub` по проверенному администраторскому каналу.
   Первое установить в `controller-access.spki` после независимого
   сравнения SHA256; второе — как отдельный `restrict,command=...`
   в `authorized_keys` (см.
   [Nodekit FI enrollment](https://github.com/grunvald91/telegram-proxy-infra/blob/main/nodekit/FI_TRUSTED_ENROLLMENT.md)).
2. Проверить root-ограничения SSH и убедиться, что обычная shell-сессия
   по выделенному ключу **недоступна**.
3. Проверить реальные миграции БД и отдельно одобрить FI inventory.
4. **Только затем**, в доверенном контроллере, выполнить
   `npm run enroll:fi-controller` с независимыми проверенными
   переменными окружения из [FI controller enrollment](fi-controller-enrollment.md).
5. После регистрации выполнить AWG signed grant/expiry/revoke E2E,
   а для персонального DNS и прокси отдельные TLS/ACL/внешние E2E.
   Клиентская публикация остаётся выключенной до этих проверок.

### Ограничения и риск-граница

Этот установщик предназначен для Ubuntu/Debian Linux с `ssh-keygen` и
Node.js. Реальная конфигурация контроллера, привилегии PostgreSQL, безопасный
канал установки публичного ключа на FI и его SSH host pin не доступны из
GitHub-репозитория и не могут считаться подтверждёнными.
Ни один секрет не следует пересылать в чат или помещать в Actions.


## Действующий контроллер и продукт Telegram-прокси

**188.120.254.223** — центральный контроллер MNEBYVPN, а не новый VPS.
Расположенные на нём сайт, Telegram-бот, PostgreSQL, entitlement-worker и
уже действующие персональные подписки сохраняются без перезапуска.
Теперь команда `init`/ `audit` проверяет локальный IPv4 RU188 и наличие
`/opt/mnebyvpn`; на FI, DE89 и новом/пустом VPS эта CLI намеренно
завершится отказом. Это не заменяет проверку реальных прав контейнеров,
миграций БД или безопасного способа установки публичных ключей.

**Прокси означает Telegram MTProto/Telemt**, уже используемый на DE89.
Nginx Stream/SNI на новых узлах — компонент Smart DNS, а не Telegram-прокси.
См. [схему](https://github.com/grunvald91/telegram-proxy-infra/blob/main/nodekit/CONTROLLER188_TELEGRAM_PROXY.md).


## Факт живого аудита / почему используется Python

18 ноября 2026 года проверка действующего контроллера через
[GitHub Actions #44284224138](https://github.com/grunvald91/telegram-proxy-infra/actions/runs/44284224138)
подтвердила: контейнеры PostgreSQL, сайта и VPN-worker работают; таблицы
`vpn_node_enrollment_inventory`, `vpn_node_enrollment_challenges` и
`vpn_awg_command_outbox` есть, но `fi-test-01` в реестре пока отсутствует.
Защищённые файлы `/root/mnebyvpn-controller` тоже отсутствовали.

Первый однократный запуск Node.js-установщика на 188 прекратился
**до генерации ключей**, поскольку на хосте нет исполняемого `node`:
[GitHub Actions #44284960356](https://github.com/grunvald91/telegram-proxy-infra/actions/runs/44284960356).
Не нужно ради этой операции устанавливать Node.js в рабочую систему или
трогать существующие контейнеры. Python/OpenSSL-скрипт с тем же форматом
ключей/manifest создаёт их **локально на 188**, с root-only правами,
без обновления ПО, БД, маршрутов или служб. Его аудит по умолчанию не
принимает публичный ключ как независимо утверждённый: требуется отдельный
контроль SHA-256 из проверенного независимого канала.
