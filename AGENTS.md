# Правила работы над MNEBYVPN

1. **Сначала диагностика и проектирование, потом установка.** Никаких изменений на существующих VPS, остановки, удаления, перезапуска прокси, изменения firewall, DNS или SSH без отдельного явного указания владельца.
2. **Сохранить текущую систему.** Не выполнять «очистку сервера», пока нет проверенных внешних резервных копий, карты активных сервисов, плана миграции и обратного переключения.
3. **Никаких секретов в Git.** SSH-ключи/пароли, токены, TLS/WireGuard/Xray private keys, subscription URLs, платёжные токены, приватные адреса/внутренние схемы, необработанные логи и `.env` не коммитить. Репозиторий публичный.
4. **Не дублировать Xray и Remnawave.** Базовые компоненты брать из официальных версионированных релизов/образов, взаимодействовать через документированные интерфейсы.
5. **Не объявлять универсальность без тестов.** Каждую комбинацию клиент / ОС / транспорт / формат подписки подтверждать тестом; HWID и автоматическое переключение не предполагать по умолчанию.
6. **Не обещать работу при белых списках.** Особые узлы добавляются только после легальных, договорных и сетевых проверок в нужных операторских сетях.
7. **Экономить GitHub Actions.** Документацию не нужно гонять через полные CI. Перед запуском определить единственный необходимый job, проверить предыдущие результаты, ограничить timeouts, не повторять ошибки вслепую.
8. **Все изменения — reviewable.** Для новой функциональности — короткие PR, тесты, журнал изменений; версии и хэши зависимостей фиксировать.
9. **Явные границы данных.** Бизнес-право доступа принадлежит MNEBYVPN backend, сетевые ключи и узлы — Remnawave; интеграция идемпотентна и восстанавливаема.
10. **Лицензии.** MIT-лицензия нашего кода не распространяется автоматически на зависимости. Соблюдать AGPL-3.0 у Remnawave и лицензии иных компонентов.

При неполных измерениях и непроверенной совместимости писать «не подтверждено», а не подменять оценку фактом.
