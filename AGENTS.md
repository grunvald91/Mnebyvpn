# Политика работы с MNEBYVPN

1. Репозиторий публичный. **Никаких** SSH-ключей, паролей, пользовательских URL подписок, платёжных токенов, дампов БД, приватных сертификатов, рабочих `.env`, настоящих схем секретных маршрутов или логов с идентификаторами.
2. Без отдельного разрешения пользователя **не менять** ни один действующий VPS, nginx, Xray, WireGuard, MTProxy/Telemt, firewall, DNS, TLS, OS; не очищать диски/данные.
3. При миграции — замеры → карта портов и сервисов → offsite backup → проверка восстановления → план отката → согласование → изолированный pilot → сравнение состояния → canary.
4. Сеть делить на **VPN**, **Smart DNS/SNI** и **control plane**. Нельзя выдавать DNS за VPN или обещать работу на всех сайтах/операторах.
5. **Никакой интеграции с Aeternia.** Можно изучать публичный принцип, но реализуется собственный сервис на открытых и разрешённых компонентах; не копировать чужие ключи/бренд/закрытый код.
6. Remnawave Node в примерах использует `network_mode: host`; перед установкой проверять реальные порты и SNI-распределение, никаких предположений о Docker-изоляции.
7. Условия лицензий upstream и версия API/SDK проверяются по конкретному релизу; не использовать `:latest` в production. Применимость AGPL оценить перед продажами.
8. ИИ-оператор может анализировать метрики и предлагать actions. Выполнение — **только allowlist**, политики полномочий, lease/lock, ограничения частоты, idempotency, audit log, health gates. **Никакого произвольного shell/root для LLM.**
9. Денежные действия — создание/удаление VPS, дорогие специальные узлы, расширение тарифа, увеличение бюджета — требуют явного разрешения владельца, пока конкретный бюджет и лимиты не утверждены. После утверждения — только внутри hard cap; при неизвестной цене действие запрещено.
10. Не давать ИИ полномочий на удаление данных, отключение безопасности, rotation критических ключей, оплату или массовую миграцию без подтверждения. При недостатке телеметрии — fail closed и уведомление, не автоскейлинг по догадке.
11. Деплой и CI — экономные, без слепых повторов; документационные изменения не требуют Actions. PR/дифф должны быть проверяемыми.
12. Отсутствие теста клиента/DoH/SNI/оператора — явно `UNVERIFIED`. Не изобретать результаты, тарифы, SLA или универсальную работу «при белых списках».
