# Политика работы с MNEBYVPN

## Подтверждённый доступ к production — читать до любых вопросов об SSH

- **Сервер 188:** реальный VPS 188.120.254.223. Доступ к нему **уже существует** через GitHub Actions репозитория [grunvald91/telegram-proxy-infra](https://github.com/grunvald91/telegram-proxy-infra), используя настроенный там защищённый secret `SERVER188_SSH_PASSWORD`.
- **Правильные workflow:** `telegram-proxy-infra/.github/workflows/mnebyvpn-main-auto-public.yml` для сайта и `telegram-proxy-infra/.github/workflows/mnebyvpn-main-auto-bot.yml` для бота (после слияния соответствующего инфраструктурного PR). Действующий ручной путь `mnebyvpn-main-bot-publish.yml`. Раньше именно эти workflow уже успешно деплоили на 188.
- **Состояние инфраструктуры:** MNEBYVPN размещается в `/opt/mnebyvpn`; используются существующие контейнеры `mnebyvpn-bot-info` и `mnebyvpn-public-web`. Не подменять этот факт неподготовленными шаблонами `~/mnebyvpn` из исходного репозитория.
- **Никогда не требовать повторного создания** `MNEBYVPN_DEPLOY_HOST`, `MNEBYVPN_DEPLOY_USER`, `MNEBYVPN_DEPLOY_SSH_KEY`, `MNEBYVPN_DEPLOY_KNOWN_HOSTS` в этом исходном репозитории: это альтернативная, не подключённая к реальному серверу схема. Проверять фактическое состояние через инфраструктурный репозиторий и его Actions, а не делать вывод «нет SSH-доступа».
- **Prodamus:** секрет `PRODAMUS_SIGN_SECRET` хранится как GitHub Actions secret в `telegram-proxy-infra` и переносится существующим `mnebyvpn-prodamus-secret-stage.yml`; не вставлять его в код или в чат.
- **Разрешение владельца от 06.11.2026:** выпуск MNEBYVPN на production после ревью и зелёного CI разрешён через уже действующий SSH-канал. Не распространять разрешение на чужие службы, сеть, proxy, nginx, TLS, firewall и прочие проекты. После выкладки отдельно проверять реальные платежи и выдачу VPN, не объявлять их работающими без E2E.

## Остальные правила безопасности

1. Репозиторий публичный. **Никаких** SSH-ключей, паролей, пользовательских URL подписок, платёжных токенов, дампов БД, приватных сертификатов, рабочих `.env`, настоящих схем секретных маршрутов или логов с идентификаторами.
2. Без отдельного разрешения пользователя **не менять** чужие сервисы действующих VPS, nginx, Xray, WireGuard, MTProxy/Telemt, firewall, DNS, TLS, OS; не очищать диски/данные. Для изолированного релиза MNEBYVPN на 188 разрешение 06.11.2026 уже предоставлено; пользоваться существующими infra workflows.
3. При миграции — замеры → карта портов и сервисов → offsite backup → проверка восстановления → план отката → согласование → изолированный pilot → сравнение состояния → canary.
4. Сеть делить на **VPN**, **Smart DNS/SNI** и **control plane**. Нельзя выдавать DNS за VPN или обещать работу на всех сайтах/операторах.
5. **Никакой интеграции с Aeternia.** Можно изучать публичный принцип, но реализуется собственный сервис на открытых и разрешённых компонентах; не копировать чужие ключи/бренд/закрытый код.
6. Remnawave Node в примерах использует `network_mode: host`; перед установкой проверять реальные порты и SNI-распределение, никаких предположений о Docker-изоляции.
7. Условия лицензий upstream и версия API/SDK проверяются по конкретному релизу; не использовать `:latest` в production. Применимость AGPL оценить перед продажами.
8. ИИ-оператор может анализировать метрики и предлагать actions. Выполнение — **только allowlist**, политики полномочий, lease/lock, ограничения частоты, idempotency, audit log, health gates. **Никакого произвольного shell/root для LLM.**
9. Денежные действия — создание/удаление VPS, дорогие специальные узлы, расширение тарифа, увеличение бюджета — требуют явного разрешения владельца, пока конкретный бюджет и лимиты не утверждены. После утверждения — только внутри hard cap; при неизвестной цене действие запрещено.
10. Не давать ИИ полномочий на удаление данных, отключение безопасности, rotation критических ключей, оплату или массовую миграцию без подтверждения. При недостатке телеметрии — fail closed и уведомление, не автоскейлинг по догадке.
11. Деплой и CI — экономные, без слепых повторов; документационные изменения не требуют Actions. PR/дифф должны быть проверяемыми.
12. Отсутствие теста клиента/DoH/SNI/оператора — явно `UNVERIFIED`. Не изобретать результаты, тарифы, SLA или универсальную работу «при белых списках».

13. **Единый источник релизных статусов:** `docs/release-gates.md`. Исторические ADR/review описывают проблемы, но не содержат независимых отметок PASS. Коммерческий MVP ограничен `docs/mvp-scope.md`. Публичные файлы не должны включать топологию, перечни нестандартных рабочих портов, прямые ссылки на infrastructure audit-runs и live IP.
14. Без правовой проверки, утверждённых тарифов и проверенных E2E не разрешать платный checkout/рекламу. Изменение текущих серверов требует отдельного разрешения. См. `docs/commercial-readiness.md`.
